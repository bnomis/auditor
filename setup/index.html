    Setting up the shared guards¶

    This guide takes you from nothing to a project whose commits and CI run the shared audit checks. It covers a new machine, a new user, a new project and an existing one.

    What you get¶

    • auditme-changed - a pre-commit hook. It sweeps the whole tree with the auditme checker, then fails the commit on any unaccepted hit in a file the commit changes, or in a file a cross-file hit names as related to one.
    • auditme-all - the same sweep reported over every file. It is published at the manual stage, and a project with no unaccepted hits also runs it on every push and in CI, so a hit in a file nobody touched still fails the push.
    • A Stop hook - a Claude Code hook that blocks the end of a turn once while an opted-in project's changed files carry unaccepted hits.
    • /auditme-project-setup - a skill that writes the config, CI workflow and project files for a new project, or adopts the hooks into an existing one.

    The checker audits the packages under src/<package>/ and the scripts in bin/. src/ is optional: a project with only bin/ is audited over bin/, and a project with no Python at all gets only the project-level checks: its uv.lock against pyproject.toml, its ruff-pre-commit pin against the ruff the audit runs, and its Markdown (spec-api-signature-drift). A .py file directly in src/ belongs to no package, so it is reported as a src-loose-module hit; move it into a package, or accept it with a line-1 marker. No other directory's Python is swept.

    A project whose Python lives elsewhere declares its roots in pyproject.toml instead, and the declared list replaces src/ and bin/:

    [tool.auditme]
roots = [
    { path = "tools/mypkg" },
    { path = "tools", modules = "top-level" },
    { path = "tests" },
]

    A directory that is not declared is not swept. See auditor check for the modules values and the errors.

    The checker also reads files outside those passes:

    • every .md file under the project, outside hidden directories and .git, .venv, node_modules, __pycache__, audit-reviews and tasks, for function signatures in a spec that no longer match the code (spec-api-signature-drift);
    • pyproject.toml and uv.lock (lockfile-drift), .pre-commit-config.yaml (ruff-version-drift) and AGENTS.md, which declares project standards some rules enforce.

    The checker's rules are described in The audit checker and in claude/skills/auditme/SKILL.md.

    Why the scopes differ¶

    The commit hook looks at changed files only, so a commit is never blocked by someone else's old hit. CI looks at the whole tree, so a hit that appears without touching its file (a cross-file duplicate, say) is still caught. A cross-file hit counts as changed when either of its files changed.

    Why the checker is pinned¶

    Projects pin the hooks to a revision of this repository (rev: in .pre-commit-config.yaml). A new rule therefore never fails a build until you choose to upgrade (see Upgrading the checker).

    Why the Stop hook is global¶

    The Stop hook is registered once, in ~/.claude/settings.json, and does nothing in a project whose .pre-commit-config.yaml lacks id: auditme-changed. It runs the installed auditor command, not the project's pinned one, so it is an early warning and the pinned hook stays the authority. In a worktree of the auditor checkout recorded in ~/.claude/auditor-source, it runs that worktree's own checker instead, so a branch that changes the checker is judged by its own version. No other repository's copy of the checker is ever run.

    A new machine¶

    Prerequisites:

    • git
    • gh, authenticated: gh auth login
    • uv, from https://docs.astral.sh/uv/
    • pre-commit: uv tool install pre-commit
    • Python meeting requires-python in pyproject.toml; the hooks run with the python3 their shebang finds on PATH
    • jq, used by the Stop hook
    • ruff, which the checker runs: the executable AUDITME_RUFF names when that variable is set (for a ruff outside the project's .venv); otherwise the project's own .venv/bin/ruff when it exists (after uv sync), whatever else is on PATH; otherwise ruff from PATH, such as uv tool install ruff. Without either, a sweep that audits a package or extra root reports ruff not installed; a project with no audit root runs only the project-level checks and does not. It must be the version the ruff hook's rev in .pre-commit-config.yaml pins; otherwise the sweep reports ruff-version-drift. Make them equal with uv add --dev ruff==<version>, or change the hook's rev

    Install:

    git clone https://github.com/bnomis/auditor.git <directory>
cd <directory>
bin/install-claude.sh

    <directory> is wherever you keep your source. The script first installs the checker as the auditor command (uv tool install --editable <directory>) and records this repository's git directory in ~/.claude/auditor-source, which the Stop hook reads. It then runs the shared installer, install-in-claude, with uvx at a pinned commit, so it needs uv and SSH access to bnomis/install-in-claude; add --dry-run to see what it would change first. It links claude/ into ~/.claude/ one level down: each directory (hooks/, rules/, skills/) becomes a real directory of symlinks to its entries. It renames any existing file in a link's place to .orig. In ~/.claude/settings.json it adds the Stop hook once. It keeps every other setting, and saves the original as settings.json.orig. It refuses to touch a settings file that is not a valid JSON object.

    The other shared rules and skills, and the status line, come from the agents repository (bnomis/agents), installed the same way with its own installer; see its docs at https://bnomis.github.io/agents/.

    Check it:

    auditor --version
ls ~/.claude/skills
grep -n 'auditme-stop.sh' ~/.claude/settings.json

    Without Claude Code, install only the checker, from a release tag:

    uv tool install git+https://github.com/bnomis/auditor@<tag>

    <tag> is a release tag of this repository. The checker runs as auditor check, auditor changed and auditor phaseb.

    A new user¶

    This repository, bnomis/auditor, is public: cloning it and running its hooks needs no access grant and no SSH key.

    The shared rules and skills in the agents repository hold nothing specific to one project. A project's own rules and skills go in its claude/ directory (claude/rules/, claude/skills/); see the agents repository's claude/rules/rule-scope.md.

    A new project¶

    In an empty repository, in Claude Code:

    /auditme-project-setup new

    It asks for the project's test command, then writes:

    • .pre-commit-config.yaml - ruff, shellcheck and both audit hooks, pinned to the current main of this repository, with auditme-all also run on push
    • .github/workflows/ci.yml - tests, the commit-time checks over the whole tree, and auditme-all
    • AGENTS.md, CLAUDE.md, TODO.md, DONE.md and claude/rules/README.md

    It installs the git hooks with pre-commit install --hook-type pre-commit --hook-type pre-push.

    No key in CI¶

    The hooks are pinned by their HTTPS URL, https://github.com/bnomis/auditor, and this repository is public, so pre-commit clones it in CI without a deploy key or secret. The workflow needs no step for it.

    An existing project¶

    /auditme-project-setup adopt

    It adds the two hooks to .pre-commit-config.yaml, and shows you any project-local runner or Stop hook doing the same job before asking to remove it.

    Then it counts unaccepted hits by rule over the whole tree:

    pre-commit run auditme-all --hook-stage manual --all-files
    • No hits: it runs auditme-all on push as well, adds the CI step.
    • Hits: it files one TODO.md item with the dated count by rule, and leaves the push stage and CI alone. Fix or accept every hit, then enable both.

    A hit is accepted with a comment on its line or the line above:

    # auditme: accept[<rule>] <reason>

    Why no gate over a backlog: a gate that fails every push gets switched off.

    Without Claude Code¶

    bin/install-hooks.sh in this repository does the hook part of adopt from a shell: it adds the auditor entry to the project's .pre-commit-config.yaml (or creates the file), pinned to the current main of bnomis/auditor, and installs the git hooks:

    $AUDITOR_PATH/bin/install-hooks.sh --dry-run <project>
$AUDITOR_PATH/bin/install-hooks.sh <project>

    <project> is a path inside the project's repository; leave it out to use the current directory. The first command prints the change; the second makes it. Add --push once the project has no unaccepted hits, so auditme-all runs on every push too. The script does not count the backlog, add the CI step. See bin/install-hooks.sh for every option.

    To enable the gates later, add stages: [manual, pre-push] under - id: auditme-all in .pre-commit-config.yaml, paste claude/skills/auditme-project-setup/templates/ci-audit-step.yml into the workflow after the project's own setup.

    Moving a project from agents¶

    A project that adopted the hooks while the checker lived in the agents repository pins git@github.com:bnomis/agents.git. That pin keeps working until the project is moved: the agents commits it names still hold the checker, so its hooks and CI run as before. They get no new rules or fixes, which land only here.

    To move it:

    1. In .pre-commit-config.yaml, change the audit hooks' repo: from git@github.com:bnomis/agents.git to https://github.com/bnomis/auditor, and their rev: to a commit of this repository: git ls-remote https://github.com/bnomis/auditor refs/heads/main, first field. The hook ids are unchanged.
    2. In the CI workflow, replace the agents deploy-key steps with the single step in claude/skills/auditme-project-setup/templates/ci-audit-step.yml, and delete the project's AGENTS_DEPLOY_KEY secret once CI passes (see Dropping the deploy key).
    3. Run pre-commit run auditme-all --hook-stage manual --all-files, and fix or accept any new hits in the same commit, as for an upgrade.
    4. If the project also pins the no-project-names hook from bnomis/agents, move it into the auditor block beside the audit hooks, keeping its args:. It moved here too, and the agents repository no longer publishes it.

    The old deploy key on bnomis/agents can then be removed.

    Dropping the deploy key¶

    A project set up before this repository was public pins the hooks by SSH (git@github.com:bnomis/auditor.git), and its workflow installs an AUDITOR_DEPLOY_KEY secret so the runner can clone over SSH. An SSH clone needs a key even from a public repository, so the URL changes first:

    1. Run $AUDITOR_PATH/bin/install-hooks.sh <project>, or change the auditor entry's repo: to https://github.com/bnomis/auditor by hand. The script moves an SSH entry to the HTTPS URL and reports cloned from https://github.com/bnomis/auditor.
    2. In the CI workflow, delete the Install the audit deploy key and Remove the audit deploy key steps, leaving the Audit the whole tree step as in claude/skills/auditme-project-setup/templates/ci-audit-step.yml.
    3. Commit, push, and check that CI passes.
    4. Delete the project's secret: gh secret delete AUDITOR_DEPLOY_KEY --repo <owner>/<project>.
    5. Remove the project's deploy key from this repository: list them with gh repo deploy-key list --repo bnomis/auditor, then gh repo deploy-key delete <id> --repo bnomis/auditor.

    Upgrading the checker¶

    pre-commit autoupdate --repo https://github.com/bnomis/auditor
pre-commit run auditme-all --hook-stage manual --all-files

    Or, from this repository, bin/install-hooks.sh <project>: it moves the auditor entry's rev: to the current main and changes nothing else in the file.

    A new rule can report hits in code that passed before. Fix or accept them in the same commit as the upgrade, so main never carries a failing gate.

    Pointing the runner at a rules repository¶

    The runner loads its checks from the rules repository that AUDITOR_RULES_PATH names. Set it per project with direnv, in the project's .envrc:

    export AUDITOR_RULES_PATH=/absolute/path/to/your/rules-repository

    Then run direnv allow and check it with auditor rules list. The repository is trusted code: the runner imports and runs it (see How it works). The runner holds no rules of its own: while the variable is unset, every command exits 2 with ERROR: AUDITOR_RULES_PATH is not set.

    Create a rules repository¶

    The runner ships a catalogue of default rules, grouped into packs. To start a rules repository from it:

    auditor rules packs
auditor rules init ~/src/my-rules --pack imports --pack security

    init writes ~/src/my-rules/selection.txt, a list of rule names. The rules of the packs you named are uncommented and the rest are commented out; with no --pack, every pack is selected. Edit the file to comment out the rules you do not want, then:

    auditor rules apply ~/src/my-rules

    apply copies the uncommented rules and their tests into ~/src/my-rules/rules, writes auditor-rules.toml, README.md, TODO.md, DONE.md and .gitignore, starts a git repository there (unless the directory is already inside a work tree) and runs auditor rules check on the result. The copy is plain: the new repository keeps no link to the catalogue, so later catalogue fixes reach it only when you copy them by hand. Then add the AUDITOR_RULES_PATH line above to the project's .envrc.

    Upgrading a project that pins the hooks¶

    Releases before 0.3.0 ran built-in rules when the variable was unset. From 0.3.0 the same rules ship as the default catalogue, src/auditor/catalogue, and a project must name a rules repository. To keep the previous behaviour:

    1. Create a rules repository: auditor rules init <dir> (see the CLI reference). To start from the default rules, copy src/auditor/catalogue from this repository into it.
    2. Add the variable to the project's .envrc, then run direnv allow:
    export AUDITOR_RULES_PATH=/absolute/path/to/your/rules-repository
    1. Set it in CI, in the job that runs the audit hooks:
    env:
  AUDITOR_RULES_PATH: ${{ github.workspace }}/rules-repository

    The CI job must have the rules repository checked out at that path. 4. Check it: auditor rules list exits 0 and lists the rules.

    Troubleshooting¶

    The hook cannot clone this repository. Run git ls-remote https://github.com/bnomis/auditor refs/heads/main. If it fails, GitHub is unreachable from that machine. If CI fails with Permission denied (publickey), the project still pins the SSH URL: see Dropping the deploy key.

    The Stop hook does not fire.

    • The project is not opted in: its .pre-commit-config.yaml must contain id: auditme-changed.
    • jq is missing: command -v jq.
    • The installer has not run: grep -n 'auditme-stop.sh' ~/.claude/settings.json.
    • No diff base resolves (no upstream, origin/main or main): changed.py prints that and passes without sweeping. Check git rev-parse --verify origin/main.
    • No reportable file changed, so changed.py skipped the sweep.
    • The directory is not a git repository: the Stop hook finds no repository root and exits 0 itself, without running changed.py.

    Hits appear only after an upgrade. Expected: the new checker has new rules. See Upgrading the checker.

    One commit must go through.

    SKIP=auditme-changed git commit

    The push and CI still sweep the whole tree, so the hit must be fixed or accepted before they pass. For one push, SKIP=auditme-all git push.
