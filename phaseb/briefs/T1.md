# T1 brief

**Brief version:** 1

You are a reviewer for one batch of a listed audit question. Judge each
candidate in the batch on its own and report one verdict per candidate.

## Security

Never list environment variables (`env`, `printenv`, `set`) or print an env
file. To test that a variable is set, use `[ -n "${VAR:-}" ]` and print only
yes or no.

## The question

**T1. Test coverage of branchy logic.** Every function with `if`/`try`/`except`/state transitions has at least one test case.

## Input

The batch file holds one JSON object per line, one per candidate. Each has
`id` (`<repo-relative path>::<qualname>`), `path`, `start` and `end` (the
candidate's lines), and a `payload` with:

- `reasons`: why the function counts as branchy (`if`, `try`, `match`,
  `state`);
- `tests`: each test the index found reaching it, as `{id, path, start, end,
  route, via, property}`; `route` is `direct` when the test calls the
  function and `caller` when it reaches it through the package function
  named in `via`;
- `callers`: the package functions that call it, to the lister's depth;
- `test_files`: the test files that import the candidate's module or a
  caller's module;
- `private`: true when the function is not part of the module's public
  surface.

Read the candidate's source and each listed test. Read `test_files` for calls
the map could not follow (a call through a fixture, an alias or a
parametrised callable).

## Thresholds

- The candidate is covered when a listed `direct` test calls it.
- For a candidate with `private: true`, a `caller` test that reaches it also
  covers it.
- An unconditionally skipped test or an `xfail` test does not count.
- A test in a file that imports neither the candidate's module nor a
  caller's module does not re-plan a candidate; `--rejudge` covers it.

A threshold that this brief does not settle is not yours to decide: report
it in your reply, name the candidate, and judge the rest as the brief says.

## Output

Write one JSON line per candidate to the result file you are given, with
exactly these keys:

- `id`: the candidate's `id`;
- `findings`: `{"missing": ["test case"]}` when it is not covered, naming the
  case that is missing, or `{"missing": []}` when it is covered;
- `reason`: one sentence on why, naming the covering test's `id` when it is
  covered.

Every candidate in the batch gets exactly one line.
