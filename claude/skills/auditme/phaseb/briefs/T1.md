# T1 brief

**Brief version:** 5

You are a reviewer for one batch of a listed audit question. Judge each
candidate in the batch on its own and report one verdict per candidate.

## Security

Never list environment variables (`env`, `printenv`, `set`) or print an env
file. To test that a variable is set, use `[ -n "${VAR:-}" ]` and print only
yes or no.

## The question

**T1. Test coverage of branchy logic.** Every function with `if`/`try`/`except`/state transitions has at least one test case.

## Input

The batch file holds one JSON object per line, one per candidate. Each has
`id` (`<repo-relative path>::<qualname>`), `path`, `start` and `end` (the
candidate's lines), and a `payload` with:

- `reasons`: why the function counts as branchy (`if`, `try`, `match`,
  `state`);
- `tests`: each test the index found reaching it, as `{id, path, start, end,
  route, via, property}`; `route` is `direct` when the test calls the
  function and `caller` when it reaches it through the package function
  named in `via`;
- `callers`: the package functions that call it, to the lister's depth;
- `test_files`: the test files that import the candidate's module or a
  caller's module;
- `private`: true when the function is not part of the module's public
  surface;
- `privacy`: the rule that decided `private`: `all` (the module's or a
  package's `__all__` names it or leaves it out), `script` (a standalone
  script, whose only public functions are those its `__main__` guard calls)
  or `underscore` (nothing is declared, so only a leading underscore makes
  it private).

Read the candidate's source and each listed test. Read `test_files` for calls
the map could not follow (a call through a fixture, an alias or a
parametrised callable).

## Thresholds

- The candidate is covered when a listed `direct` test calls it.
- For a candidate with `private: true`, a `caller` test that reaches it also
  covers it. With `privacy: script`, a test that loads the script by path
  (`runpy`, `importlib.util.spec_from_file_location`) and runs an entry
  point that reaches the candidate is such a test, listed or not.
- An unconditionally skipped test or an `xfail` test does not count.
- A test in a file that imports neither the candidate's module nor a
  caller's module does not re-plan a candidate; `--rejudge` covers it.
- A call to a package's re-export of the candidate (`from pkg import
  load`, then `load()`) is a call of the candidate: it is the same object.
- A call through a `functools.singledispatch` generic, a dispatch table or a
  parametrised name covers each implementation the test's own arguments or
  parameters reach, and no other.
- A dunder the language runs - `__post_init__` by constructing,
  `__str__`/`__repr__`/`__format__` by `str()`, `repr()`, `print` or an
  f-string, `__getattr__` by reading a missing attribute - is called by the
  test that does so.
- A call made by a wrapper is the wrapper's: a test of a one-line `__str__`
  that forwards to `summary()` covers `__str__`, and a public `summary`
  still needs a test of its own.
- A call made by a helper defined in the test file, which the test calls,
  is the test's own call.
- A test that runs a script's path as a subprocess (`subprocess.run` with
  `sys.executable` and the path, or the path itself) is a caller test of each
  `script` candidate the script's `__main__` entry point reaches, like a
  `runpy` load.
- A fixture the test uses - requested as a parameter, named in
  `@pytest.mark.usefixtures`, or `autouse=True` in the test's file or a
  `conftest.py` above it - is part of the test, and its calls are the test's
  own calls. A fixture the test does not use in one of those ways is not.
- A test that passes the candidate as an argument covers it when the package
  function receiving it calls that argument on the path the test takes. Read
  the receiver. Passing it only to store, register or compare it does not
  cover it.

A case this brief does not settle is not a finding: judge it not flagged,
name the candidate and the case in your reply, and judge the rest as the brief
says. Every reviewer gives an unsettled case the same verdict, so it does not
depend on the batch; the operator settles a reported case when it should count.

## Output

Write one JSON line per candidate to the result file you are given, with
exactly these keys:

- `id`: the candidate's `id`;
- `findings`: `{"missing": ["test case"]}` when it is not covered, naming the
  case that is missing, or `{"missing": []}` when it is covered;
- `reason`: one sentence on why, naming the covering test's `id` when it is
  covered, and the `privacy` rule whenever `private` decides the verdict.

Every candidate in the batch gets exactly one line.
